# Smart Cinema Physical Data Dictionary v1.0

Date: 2026-09-25  
Status: Proposed PostgreSQL design; V1/V2 are existing, all other definitions are not implemented.

## 1. Scope and source authority

This dictionary maps all 20 entities in the [canonical Mermaid ERD](erd/smart-cinema-logical-erd.mmd) and [logical documentation](erd/smart-cinema-logical-erd.md). It implements the choices in [database design decisions v1.0](database-design-decisions-v1.0.md) at the design level. Read it together with the [integrity-enforcement design](integrity-enforcement-design-v1.0.md); column constraints alone do not implement the transaction invariants.

Business authority remains [BRD v1.2](../brd/brd-v1.2.md) and [SRS v1.2](../srs/srs-v1.2.md), especially SRS §§3.5–3.10, 4.2 and 5.1–5.18. No requirement, existing migration or logical ERD is rewritten. This is documentation, not executable migration DDL. PostgreSQL 18 documentation is the technical reference, consistent with earlier repository database verification; the actual deployment version must be checked before migration authoring.

### Physical refinements of the logical model

Only three supporting columns are added beyond the logical attributes/descriptive fields already documented:

| Column | Reason | Authority |
|---|---|---|
| `showtime_seats.hall_id` | Shared discriminator for two composite FKs proving Seat and Showtime use the same Hall | Derived from immutable parent membership; never client-authoritative |
| `booking_seats.sold_at` | Materialized sale marker supporting a unique successful-sale constraint while retaining failed Booking history | Set only with PAID finalization, equals Booking.paid_at; cannot be cleared |
| `showtimes.occupied_until` | Preserve the configured Hall buffer boundary for an overlap exclusion constraint | Server-computed schedule snapshot, at least end_time |

These are enforcement attributes, not new business entities. The logical ERD remains at its approved abstraction level. No independent cached HELD/BOOKED column is added to `showtime_seats`.

## 2. Common physical rules

### Types, nullability and defaults

- Each `id`: `bigint GENERATED BY DEFAULT AS IDENTITY`, NOT NULL, PK. This matches existing Auth identity style. IDs are immutable; explicit IDs are reserved for controlled data import, not customer input.
- Every identifier FK uses `bigint`. PK name for new tables: `pk_<table>`. Existing generated names are preserved.
- `NN` in tables means NOT NULL; `NULL` means optional. `—` means no default: a valid insert must supply NN values. `identity` means the identity generator. Lists of columns in one row all share the shown type/nullability/default.
- `T` abbreviates `timestamp(6) with time zone`; existing V1/V2 use unqualified `timestamp with time zone` and remain byte-for-byte unchanged. Calendar release dates use `date`. Store instants and use UTC database sessions; convert branch-local display times at the boundary. PostgreSQL timestamps do not preserve a named source time zone. [PostgreSQL date/time types](https://www.postgresql.org/docs/18/datatype-datetime.html).
- New stored timestamps/dates must be finite; use `isfinite(column)` (nullable values allow null). Existing Auth checks are not retroactively strengthened.
- New human-readable required text has `btrim(value) <> ''`; optional text has `value IS NULL OR btrim(value) <> ''`. Empty strings are not substitutes for null. Code fields use ASCII uppercase where specified; free text supports Unicode. URLs are bounded strings validated by the service, not fetched by database checks.
- JSON values use `jsonb`, default `{}` where shown, with `jsonb_typeof(value) = 'object'`; store only safe bounded metadata. Do not turn JSON into an alternate store for relational ownership or pricing.
- No blanket created/updated columns are invented. Only source-listed timestamps and the three refinements above are included. Updating master rows does not rewrite transaction snapshots.

### Money and currency

`M` means `numeric(19,4)`: up to 15 integral digits and four fractional digits. Do not use floating point or PostgreSQL's locale-dependent `money` type. Every price/amount/discount has `0 <= value AND value < 1000000000000000`; this also excludes NaN and infinities. For nullable amounts, allow null explicitly. Exact numeric precision is documented by [PostgreSQL numeric types](https://www.postgresql.org/docs/18/datatype-numeric.html).

Four fractional digits are storage capacity, not a promise that a gateway accepts four-digit minor units. The service uses decimal arithmetic, rounds payable values once to the configured currency's minor-unit scale using decimal HALF_UP as the selected technical rounding convention, and rejects nonrepresentable gateway amounts. It validates incoming precision before persistence rather than relying on implicit column rounding. Catalog publication validates prices against the configured currency scale; all Booking/line totals must already be consistent at the payable scale. Do not round each callback differently. Currency scale/provider support and the business discount basis still require confirmation before enabling a provider/promotion.

The single-chain MVP uses one configured pricing currency for its catalog. Currency changes while old priced Bookings remain payable are prohibited operationally. The first Payment Transaction pins currency for that Booking and subsequent attempts match it. `currency` is `varchar(3)` with `^[A-Z]{3}$`; allowed currency codes/scales are configured, not a new currency table. No exchange-rate or mixed-currency Booking behavior is introduced.

`seat_amount = sum(booking_seats.final_price)` and `concession_amount = sum(booking_concessions.total_price)`. `final_price` means the seat line amount before the separate Booking-level `discount`; do not count the same discount in both places. No per-line allocation of Booking discount is introduced. Choosing whether a Promotion applies to Seats, Concessions or the whole Booking remains an explicit business-policy prerequisite, as required by SRS §3.8.

### Status and enum storage

Use `varchar` plus named CHECK constraints, not PostgreSQL ENUM types or new lookup entities. Tokens are UPPER_SNAKE_CASE. Complete new-table sets below are proposed storage encodings of existing lifecycle meanings, not new business functions. Membership checks do not enforce transitions; the enforcement document specifies those.

| Field family | Allowed values / treatment |
|---|---|
| User role/status | Preserve V1 exactly: four roles; status only nonblank; no new status restriction in this task |
| Cinema status | ACTIVE, TEMPORARILY_CLOSED, INACTIVE (Business Analysis vocabulary) |
| Hall status | ACTIVE, MAINTENANCE, INACTIVE |
| Seat physical status | ACTIVE, MAINTENANCE, INACTIVE; proposed encoding of physical condition, distinct from sale availability |
| Seat type / snapshot | STANDARD, VIP, COUPLE |
| Assignment type/status | STAFF or MANAGER; ACTIVE or INACTIVE; these encode assignment scope/deactivation, not employee HR states |
| Movie status | Nonblank UPPER_SNAKE_CASE `^[A-Z][A-Z0-9_]*$`; exact catalog vocabulary remains an approved configuration prerequisite, not guessed from release dates |
| Showtime status | DRAFT, SCHEDULED, OPEN_FOR_BOOKING, STARTED, ENDED, CANCELLED |
| Hold status | ACTIVE, RELEASED, EXPIRED, CONSUMED; technical record lifecycle, not the availability projection |
| Booking status | PENDING, PAID, EXPIRED, CANCELLED |
| Concession / Promotion status | ACTIVE, INACTIVE; optional DRAFT omitted for minimal scope |
| Concession category / snapshot | Nonblank UPPER_SNAKE_CASE, configured vocabulary including POPCORN, DRINK, COMBO; no separate category entity |
| Promotion discount_type | FIXED, PERCENTAGE; selected encodings of the supported discount-type concept; business scope still unresolved |
| Payment status | INITIATED, PENDING, SUCCESS, FAILED, CANCELLED; no REFUNDED state in MVP |
| Ticket status | VALID, CHECKED_IN, EXPIRED, CANCELLED; CHECKED_IN is terminal; do not persist USED as a second synonym |

| Child columns | Referenced table and columns | Purpose |
|---|---|---|
| showtime_seats(showtime_id,hall_id) | showtimes(id,hall_id) | Screening Hall |
| showtime_seats(seat_id,hall_id) | seats(id,hall_id) | Same physical Hall |
| seat_holds(showtime_id,seat_id) | showtime_seats(showtime_id,seat_id) | Configured pair |
| booking_seats(showtime_id,seat_id) | showtime_seats(showtime_id,seat_id) | Configured pair |

Hold attachment FKs use MATCH SIMPLE: booking_id null means unattached; showtime_id/seat_id/user_id remain independently NN and validated by pair/User references. All fit PostgreSQL identifier limits.

## 5. Unique keys, checks and indexes

### Unique constraint registry

Every table has its PK; do not add duplicate ordinary indexes for PK/UNIQUE keys. Normal nullable uniqueness allows many nulls. PostgreSQL documents automatic indexes and null behavior in [constraints](https://www.postgresql.org/docs/18/ddl-constraints.html).

| Name | Table / columns | Reason |
|---|---|---|
| uq_users_email | users(email) | Existing V1 |
| uq_refresh_tokens_token_hash | refresh_tokens(token_hash) | Existing V2 |
| uq_movie_genres_pair | movie_genres(movie_id,genre_id) | No duplicate Genre link |

### Showtime schedule exclusion

Select `ex_showtimes_hall_occupancy`: GiST exclusion of equal hall_id with overlapping `tstzrange(start_time,occupied_until,'[)')`, for rows whose status is not CANCELLED. This includes DRAFT: two saved candidate Showtimes must not conflict; cancellation releases scheduled occupancy. Use PostgreSQL `btree_gist` for bigint equality with range overlap; this is a future migration dependency, not installed now. Half-open intervals allow the next Showtime at occupied_until. [Range exclusion constraints](https://www.postgresql.org/docs/18/rangetypes.html#RANGETYPES-CONSTRAINT), [btree_gist](https://www.postgresql.org/docs/18/btree-gist.html).

Checks are named `chk_<table>_<rule>`: type/status membership; nonblank text; finite dates; monetary range; duration/capacity positive; Showtime times; Hold expiry; Booking arithmetic and paid fields; concession quantity/arithmetic; Promotion period/value; payment completion; Ticket check-in pair/order; JSON object/system attribution. Predicates are specified in §§2–3. They must be row-local and explicitly NULL-safe. Cross-table totals, payment authenticity, expiry-now and state transitions are not CHECK expressions.

## 6. Delete and update policies

New FKs: `ON UPDATE NO ACTION ON DELETE NO ACTION`; immediate by default, with only the origin-Hold-to-line FK deferred as specified. Existing V2 uses PostgreSQL's default NO ACTION actions and is preserved. IDs and membership are immutable under write guards, so no cascading key update is required.

- No cascading delete of Users, Bookings, Holds, payments, Tickets, audit or referenced master records. Account deletion is not implemented by this design.
- Master records use approved status deactivation. Unreferenced catalog configuration may be deleted only by an authorized administration path that validates lifecycle and audit obligations; existing references block it.
- Pending, unfrozen concession lines may be removed per FR-BOOKING-017. Seat lines and origin Holds are retained; changing Seats uses a new Booking. Frozen line deletion/update is rejected by guards.
- `movie_genres` unlink is allowed by catalog administration; it does not delete Movie/Genre parents. `showtime_seats` membership is immutable once Hold/Booking history exists; sale eligibility may change without erasing history.
- Transactions and audit are retained. Privileged maintenance/retention procedures require a separate approved policy and may not disable guards casually. No automatic TTL delete is assumed for refresh tokens or Holds.

## 7. V1/V2 reconciliation and future rollout

Keep [V1](../../backend/src/main/resources/db/migration/V1__create_users_table.sql) and [V2](../../backend/src/main/resources/db/migration/V2__create_refresh_tokens_table.sql) unchanged. New domain FKs reference the existing `users.id bigint`; no duplicate account table, type conversion or role split. V1/V2 column defaults and checks take precedence over new-table conventions in this dictionary.

Existing gaps remain explicit: V1 accepts nonblank status beyond the Java ACTIVE/BLOCKED set; SQL does not update updated_at automatically; V2 does not require exact hexadecimal hash length or revocation chronology. Any later tightening requires stored-data assessment and a new forward Flyway migration; it is not silently included in the proposed domain baseline.

Future authoring order: catalog and organization parents; Showtimes/pairs; Bookings and lines; Holds with origin references; Payment/Tickets/Audit; guards, deferred assertions and constrained write interfaces as one coherent rollout. Stage cross-references before enabling writes, validate existing data before enabling new constraints, check `btree_gist` availability, verify migration version allocation then. No V3 filename or executable DDL is created now.

Business-policy prerequisites remain: Promotion scope/usage reservation, Movie status vocabulary, provider reference/currency contracts and physical seat-label overlap validation. The [enforcement design](integrity-enforcement-design-v1.0.md) identifies how these boundaries affect rollout without inventing an unrelated entity.
