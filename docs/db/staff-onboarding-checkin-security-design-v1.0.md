# Staff Onboarding and Check-in Security Design v1.0

Date: 2026-10-12; contract-first design before Java/V13. Source head V12. Preserve V1–V12 and all financial writers/guards. [Staff operational contract](../api/staff-qr-checkin-contract-v1.0.md), [onboarding contract](../api/staff-invitation-administration-contract-v1.0.md).

V13 adds designed cinema_assignments plus staff_onboarding, staff_invitations, staff_invitation_deliveries and staff_rate_limits. No plaintext token/password stored. Dedicated NOLOGIN smart_cinema_staff_owner manages onboarding/admin/queue, smart_cinema_checkin_owner owns Ticket command. Runtime gets narrow EXECUTE, no DML/owner membership/PUBLIC privileged helpers. Fixed pg_catalog,pg_temp search_path and qualified actual schema support isolated migration tests.

Actor/target User rows lock in deterministic ID order before Cinema/scope/child resources. Staff blocking/revocation locks target User UPDATE; admission locks actor SHARE then uses existing parent/resource gate through a private hold-owner lock-only adapter. Do not pass Staff to the Customer-only lock_hold_context actor branch. Preserve integrity v1.1 order; time after all waits. All selected Tickets validate before update/audit. Check-in owner lacks Payment result EXECUTE and Payment/provider DML.

Ticket-specific guard preserves hold-owner settlement INSERT, denies DELETE and allows checkin-owner VALID→CHECKED_IN touching only status/checked_in_at/checked_in_by_user_id. Finite time/current Staff/scope and immutable identity. Dedicated audit guard preserves existing financial append-only behavior and narrowly allows Staff management events and canonical TICKET_CHECKED_IN. Unique per-Ticket action plus deferred transition/audit correspondence prevents audit-only success or partial commit; historical audit doesn't require operator remain ACTIVE later.

Onboarded User guard prevents direct credential/status/role mutation outside staff-owner functions while leaving historical non-onboarded Auth fixtures/Customer flows intact. Invitation has exact 24-hour lifetime, purpose-bound unique digest, consumed/revoked state; one outstanding token per Staff. User-first locked redemption hashes an eligible password in the service and atomically consumes invitation plus sets passwordSetAt, retaining BLOCKED. ADMIN activation requires setup. Block/reissue invalidate old outstanding invitations and wipe payloads, preserve assignment history. No recovery workflow for completed accounts.

Encrypted queue commits with account/invitation intent. Claim/completion transactions only lock delivery rows and never acquire earlier domain locks afterward; SMTP/crypto work occurs outside transaction. Domain reissue/block/redemption enters User→invitation→delivery order. Leased delivery can race revocation, but delivery lease never authorizes redemption. Completion rechecks live invitation state; stale SMTP messages cannot restore token validity. Active/previous AES-GCM keys are external 32-byte secrets, kid+nonce+ciphertext only persisted, AAD binds account/digest/purpose. Delete ciphertext on terminal status, supersession, consumption or expiry. Encrypted backups still require normal secret management; no durable unencrypted link payload.

Technical timeout/rate/retry bounds are explicit contract/configuration, not new admission or Ticket business rules. Public redemption uses durable hashed-peer bucket; resend uses actor bucket. Mail disabled by default; missing credentials/key/config never becomes successful mail. Tests override SMTP to loopback capture and use only isolated local database schemas. Gmail real delivery/production and full activation frontend are NOT VERIFIED/NOT IMPLEMENTED by this phase.
